# Security model and limitations

nucube runs user-authorized code on a local machine. It is **not hardened isolation for hostile multi-tenant workloads**. Every local user able to call the unauthenticated loopback API can submit code within policy; use a trusted single-user environment. Never expose/forward this port remotely. No CORS is enabled; browser-origin requests and unexpected Host headers are rejected to reduce cross-origin/DNS-rebinding risks. These controls are not authentication.

Docker daemon access is privileged. Workers never receive the Docker socket, arbitrary host mounts, controller environment, or host credentials. They run under the host user's nonzero uid/gid (65534 when the controller runs as root), with all capabilities dropped, no-new-privileges, read-only root, default Docker seccomp, bounded PIDs, CPU/memory limits and no swap beyond the memory allocation. Source/input mounts are read-only. `/tmp` is a bounded, noexec/nosuid tmpfs. `/output` is a dedicated per-attempt writable directory. Network defaults to none; the controller must explicitly allow requests to enable bridge networking. Image entrypoints are overridden; commands are argument arrays.

Only approved, pre-pulled images run. Approve image digests for reproducibility. Image content and Docker/kernel vulnerabilities remain trust boundaries. Docker/VM and host resources are shared; configured capacity does not account for unrelated workloads. Limits do not guarantee performance.

Snapshots and collected files reject traversal, symlinks, hardlinks and nonregular files. Reads use directory-relative file descriptors with O_NOFOLLOW and bounded byte reads. Artifacts are only readable through published manifests. Output collection happens after the worker exits/is killed. A trusted host user can still mutate storage; the artifact store is not tamper-proof. Keep storage private to the controller user and use a local filesystem that supports locks and atomic rename.

## Disk and deadline limitations

Snapshot bytes and file counts are bounded. Output collection is bounded per attempt and refuses unsafe/oversized trees. However, the writable bind-mounted `/output` has **no live disk quota**: a running worker can fill host disk before collection. Partial/failed outputs consume disk until retention. Docker's local logging driver rotates at the configured cap (rounding/chunk overhead may occur); API logs are additionally truncated. Job/attempt metadata and idempotency keys are retained indefinitely. Submission crashes can leave unreferenced snapshot directories. Monitor disk space and use a quota-controlled filesystem for stronger containment; this MVP is not suitable for untrusted disk-abuse workloads.

Container runtime deadlines depend on the controller scheduler or independently scheduled reaper. Docker itself does not enforce these wall-clock deadlines. Polling and Docker RPC latency can overshoot deadlines; during controller outages, configure periodic `nucube reap --expired`. A failed Docker daemon can prevent timely termination. The reaper verifies ownership labels and installation ID before cleanup and leaves other installations and unlabeled containers alone. Labels protect accidental cleanup, not malicious users who already control Docker.

Outputs/logs are untrusted content, including potential prompt injection. Consumers must not interpret them as instructions. Enabling network expands risk to external side effects; retryable programs must be idempotent. nucube has no dollar-budget enforcement, cloud provisioning, multi-user auth, secrets injection, privileged worker mode or arbitrary mount configuration.
